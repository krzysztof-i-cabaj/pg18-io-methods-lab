REPACK (CONCURRENTLY) in PostgreSQL 19: no write stall under light traffic, a stall at the end under heavy traffic

We measured the cleanup of a bloated 2.3 GB table while 1, 4 or 8 sessions keep writing to it. Under light traffic the new command really does not stop writes, while the old VACUUM FULL blocks them for 11 s. As traffic grows the advantage shrinks, and with 8 sessions REPACK blocked longer: 18 s versus 15 s.

Where the problem comes from: the table file does not shrink by itself

On UPDATE and DELETE PostgreSQL does not overwrite a row in place. The old version stays in the file, because another transaction may still need it (MVCC).

A plain VACUUM marks that space as free for reuse, but does not return it to the operating system. In our test, after deleting half of 20 million rows the file was still 2.3 GB.

To get the disk space back, the table has to be rewritten into a new, compact file that replaces the old one. The question is what happens to the application meanwhile.

How both commands work: the same job, a different lock

Both build a new copy of the table. What differs is how strongly they hold the table meanwhile and when the application has to wait.

VACUUM FULL

An ACCESS EXCLUSIVE lock from the first to the last second: nobody reads or writes this table. The rest of the database keeps working.

REPACK (CONCURRENTLY)

Copies under SHARE UPDATE EXCLUSIVE, so the application keeps reading and writing. Changes made meanwhile are captured with logical decoding (it uses a slot from max_repack_replication_slots, 5 by default).

Final phase

Under ACCESS EXCLUSIVE it applies the last captured changes and swaps the files. These are the only seconds when writes stall. A primary key or a replica identity index is required.

Why the end grows with traffic

Think of moving a library. VACUUM FULL locks the door and rearranges every book. REPACK (CONCURRENTLY) builds new shelves next door while readers keep borrowing, and every loan goes into a notebook. At the end the door is locked, the notebook is copied over and the signs are switched.

The more loans meanwhile, the thicker the notebook and the longer the door stays locked. That is how our numbers line up: 0 s of full lock with 1 session, 5 s with 4 sessions, 18 s with 8 sessions. The whole operation gets longer too: 14 → 32 → 93 s.

The documentation says the same in one sentence: the lock is typically held for a short time, depending on the amount of changes accumulated while the lock was being waited for. Our measurement shows what “short” means in seconds.

The library is our analogy. With 8 sessions the 4 CPUs of the VM are fully busy, so part of the slowdown is plain CPU contention. Not tested: a long transaction reading the table may also delay the final phase, because REPACK then waits for its lock and writes queue up behind it.

What to do about it

Run it off-peak

Under light traffic REPACK (CONCURRENTLY) really does not stop writes. The quietest time for the table shortens the final phase.

Give the application room to wait

The final phase blocks reads of this table too. Check lock_timeout and statement_timeout on the application side: a few seconds of waiting must not end in an error for the user.

Measure the end on your own system

In PG19 log_lock_waits is on by default: the log shows acquired … after 5818 ms, i.e. how long sessions waited. Under heavy traffic compare it with a maintenance window.

How we measured

VM pgio: Rocky 9.8, 4 vCPUs, 3.6 GB RAM, data disk on a virtual NVMe controller. PostgreSQL 18.6 and 19.0 from PGDG side by side with the same configuration (shared_buffers = 1GB); one cluster runs during a measurement, started with an empty cache.

Table bloat_t: 20 million rows, DELETE of every second row, a plain VACUUM. Writes: pgbench with 1, 4 or 8 sessions, each running an UPDATE of a random row by primary key, logged every second. The operation starts after 10 s of traffic.

What these numbers do not show

The seconds come from one VM. What carries over is the shape: the lock at the end and its growth with traffic. We measured writes only; according to the documentation ACCESS EXCLUSIVE blocks reads too. Only the table being cleaned up is blocked, not the whole database.

Two conditions from the documentation that the measurement does not show: REPACK (CONCURRENTLY) is not MVCC-safe (a transaction with a snapshot taken before it started sees an empty table afterwards; VACUUM FULL does not have this flaw), and with more than about 104 million rows changed meanwhile the command aborts.
